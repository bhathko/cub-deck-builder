# check-outline — 產檔前大綱健檢(規則本體)

> 本檔是健檢流程的**單一真相來源**,GPTs 與本機 Codex CLI 共用。
> 本機前端見 `.codex/skills/check-outline/`(只內聯環境差異:沙箱路徑改
> `ppt_out/`,其餘規則照本檔)。

三支流程的分工:**check-outline 出報告(不動稿)→ enrich-outline 陪改稿
(`[補]` 標記 + 豐富鏈稽核)→ outline-to-ppt 產檔**。本流程是唯讀健檢:對照
頁型契約與模板實際容量,告訴使用者這份內容能做出什麼、會卡在哪、怎麼改最划算。
**使用者一開口就是要產檔(沒有要建議)→ 直接走一鍵產檔,不要先塞健檢。**

規則依據(不在本檔另寫一份):

- `page_types_registry.md` — 槽位契約;**字數與清單長度一律以檔尾「light 模板的
  實際容量」表為準**(那是量測值,各節散文只講語意與結構、刻意不寫數字)
- `tools/README_TOOLS.md` — 候選規劃與整庫覆蓋審視的判準
- `enrich_outline_skill.md` — 增補三類與防捏造邊界(建議「要補內容」時引用)

## 鐵律

1. **只檢查與建議,不改稿**:不覆寫使用者的大綱、不代寫核准版、不建 spec、
   不產檔。示範縮寫可以,但不得動數字、不得改原意;缺的數據只能列成
   「請提供」清單,嚴禁在建議裡示範捏造(不寫「例如:效率提升 30%」)。
2. **頁型全集一律動態跑 `make_skeleton.py --list`**,不得照任何文件寫死的
   數量自我設限;使用者指名模板時加 `--template-pack <模板id>` 查該包集合。
3. **每條建議都要標依據與效果**(依據=容量表/頁型契約/稽核規則;效果=解鎖
   哪個頁型、避免哪個 FAIL),不給空泛的「建議豐富內容」。
4. **字數與上限不目測、不翻文件抄數字**,用容量探針(直讀 validator + 模板包
   manifest 的合併容量,與 spec 閘門永遠同步;計字語意同閘門):

   ```
   python /mnt/data/tools/capacity_probe.py --list-caps <頁型>
   python /mnt/data/tools/capacity_probe.py --check <頁型> <槽位> "候選字串"
   ```

   清單槽位給整數驗項數;使用者指名模板時加 `--template-pack <模板id>`。
5. **不確定就標 `【NEED HUMAN】`,不擅自替使用者假設**:凡是判斷取決於使用者
   意圖(對象、場合、頁數、先後關係)或缺料(數據、日期)的點,就地標記並
   化成具體問題,集中在報告結尾一次問(最多 5 題,挑最影響產出的);每題必附
   「答了會改變哪條建議」,不問答了也不影響結果的題。使用者不答或說「就這樣
   做」→ 用保守預設繼續(預設模板、不猜數字、湊不出就略過 agenda),不糾纏
   ——健檢可以發問,產檔流程中途仍照它自己的規則不發問。

## 流程

0. 先跑產檔流程的 Step 0 環境準備(解 tools.zip 與模板包、確認 validator 在位)。
1. **先認輸入類型**:
   - 貼的是 **slide_spec.json**(或自稱 spec 的 JSON)→ 不套大綱健檢:存檔後跑
     `python /mnt/data/validate_slide_spec_gpts.py --spec <spec> --asset-dir /mnt/data`,
     把每條錯誤對照 `README_TOOLS.md` 的錯誤→修法表翻成白話建議(仍不代改、
     不產檔);全過就告知可直接走直供 JSON 模式產檔。
   - 貼的是段落文字/大綱 → 走下面的大綱健檢。
2. `python /mnt/data/tools/make_skeleton.py --list` 取當前頁型全集。
3. 對照原文出六節健檢報告;各節內凡判斷取決於使用者意圖或缺料的點,行內標
   `【NEED HUMAN】` 並化成具體問題(鐵律 5):
   - **輸入格式**:格式亂也要能給重排建議,不是只說「切不出頁」——整團未分段
     的文字、沒有標題/條列階層、表格貼壞黏行、編號斷裂、貼上時斷行破碎等,
     逐項指出並示範重排方式(分段、每個主題配一行小標、長句條列化;示範只重排
     使用者自己的字句,不新增內容、不動數字)。標明效果:切頁與 `source_excerpt`
     對映更準,減少稽核/驗證 FAIL。
   - **可切頁性**:封面主標可否提煉到上限內?agenda 湊得出允許區間的項數嗎
     (上限與區間跑 `capacity_probe.py --list-caps cover` / `--list-caps agenda`
     查現值;湊不出就建議略過,不硬湊)?至少一頁真內容頁且標題有來源支持?
     整份擠不出任何一頁才算「來源不足」,如實回報。
   - **結構多樣性**:盤點原文具備/缺少哪些語意結構(時序、循環、對比、層級、
     數據、分類……對應 `--list` 的 `stage_*`/`cycle_*`/`data_*`/`pyramid_*` 等
     家族),預估可解鎖的頁型;內容頁多但預估 unique 頁型 ≤2 → 點名雷同風險,
     給具體改寫方向(例:「三個做法若改寫成有先後的步驟,可解鎖 `stage_*`
     時序頁」)。**已經有候選規劃時改用機械依據**:
     `make_skeleton.py --plan … --gap-report <path>` 會直接算出「這頁再補幾段
     內容就能換哪個版型」,比憑感覺預估準,建議一律以它為準。
   - **容量風險**:關鍵字串(主標、候選頁的標題與要點)逐一過探針 `--check`,
     把 FAIL 的照探針輸出點名(它會報超幾字),並示範不動數字、不改原意的縮法、
     示範句再過一次探針確認 PASS。**系統不會縮小字級遷就**——字級是設計過的,
     塞不下就要改稿或換頁型(產檔後 qa 會把縮字列為 FAIL)。
   - **佔位與缺料**:哪些頁會出現「待補充」;KPI/數據頁沒有現成數值時系統不得
     自選,想要就得提供數字——逐項列「請提供」清單。
   - **素材**:原文點名圖片/圖表的需求 → 說明本管線不生圖(全部 PowerPoint
     可編輯物件),外部檔案須放進素材根;可改口述資料由版型呈現的就建議改法。
4. 報告結尾先集中列 **NEED HUMAN 清單**(把各節的 `【NEED HUMAN】` 與「請提供」
   數據題合併編號,每題附「答了會改變哪條建議」;≤5 題)。常見題型舉例——不是
   必問,挑對這份內容真有影響的:
   - 「這份要對誰報(對內進度/對外提案)?→ 影響結構多樣性節建議的頁型家族」
   - 「這三個項目是並列還是有先後?→ 決定建議 `info_*` 還是 `stage_*` 家族」
   - 「有改善前後的數據嗎?→ 有才建議 `data_*` 頁,沒有就不列」
   - 「有指定模板嗎?→ 決定用哪張容量表重查」

   收到回答後**只更新受影響的建議條目**,不整份重寫;之後給下一步三選一,
   等使用者決定,不代跳:
   - **直接產檔**(內容已夠)→ 走一鍵產檔。使用者自己改完稿貼回也走這條——
     使用者是作者,不需 `[補]` 標記。
   - **要陪著補內容** → 走 `/enrich-outline`(增補行標 `[補]`,管線帶
     `--original` 驗豐富鏈)。
   - **先補資料** → 等使用者提供「請提供」清單的數據後重新健檢或直接產檔。
