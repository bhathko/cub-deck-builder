VOCABULARY · 記住這三個詞,整套系統就講完了

三個關鍵詞

01 · IDENTITY
key 對照
認元件只看 Figma 元件的身分證字號(key),完全不看名字。名字會改、會打錯;key 不會。人做過的判斷釘在 key 上,同一個元件最多只被問一次。
38,021 個淘汰實例 · 名字比對只抓到 13 個
02 · RULES
recipe 食譜
每種元件一份「怎麼從設計稿參數煮出 Angular 碼」的固定作法。食譜是程式,不是 AI——同樣的輸入,永遠產出同樣的程式碼。
29 份 · 表單 / 表格 / 卡片 / 頁籤 / 日期選擇器
03 · DATA GAP
manifest 資料洞
設計稿畫得出「長相」,畫不出「資料」。缺的資訊留一個結構化的洞問人,絕不編造;答過的答案入庫,不再問第二次。

ZERO SILENT DROP · 每個圖層都要有下落

鐵律:0 無聲丟棄

無聲丟棄 = 設計稿上有、產出裡沒有,而且沒有告訴任何人。破版看得見,看得見就有人修;消失的東西沒人找,還會讓畫面「看起來更乾淨」,一路活到驗收。合法的下落只有四種:

— 01 / 帳上有
轉成元件

認得,照食譜煮。畫面上看得到元件。

— 02 / 帳上有
轉成版面

容器、排版結構。畫面上看得到排版。

— 03 / 帳上有
登記「忽略」

純裝飾圖形、隱藏圖層。畫面上刻意不留——所以驗收看覆蓋率報告,不要數框。

— 04 / 帳上有
佔位框 + 待辦

認不得。畫面上是誠實的框,同時進待辦清單。

不存在第五種「就這樣不見了」。
進來 100 個圖層,帳上就要有 100 個去向 · 帳不平當場失敗,不硬吐缺件的頁面

PAINPOINTS · 砍掉 AI 之後,坑從「AI 亂猜」變成「自己的盲區」

六個真實的坑

01 · 裁判有盲區
通過編譯,畫面是壞的

表單容器放了不合格的控制元件,ng build 一路通過,頁面一開直接報錯。

→ 加無頭瀏覽器實開驗證
02 · 無聲丟棄
整張表格無聲蒸發

淘汰判斷靠名字比對(命中率 0.03%),漏網的整張表格消失,零錯誤訊息。

→ 全專案最忌諱的一類 bug
03 · 無聲空白
有產出 ≠ 有畫面

時間軸元件初始資料是空陣列,畫面一片空白,系統還回報一切正常。

→ 空狀態必須有預覽假資料
04 · 最危險的一類
自信的捏造

按鈕文字被寫死成「取消/確認」;對照設計稿,真實按鈕是「林小可」「前往待辦案件」。

→ 錯得很合理,才會活到驗收
05 · 判準太寬
子字串誤殺

「it info」剛好是「credit info」的尾巴,Credit Info 整塊被當外殼剝掉。

→ 剝殼只准丟外框,不准丟內容
06 · 退路的代價
退路把失敗偽裝成成功

彈窗找不到內容區就「退回整張 frame」,整頁被吞進彈窗、待辦清單卻是空的。

→ 修法:拿掉退路

PATTERNS · 程式碼搬不走,模式搬得走——不限框架、不限工具

六個可復用的模式

01
確定性優先,AI 放邊緣

能寫成規則的絕不用 AI;AI 只放在「錯了也無害」的位置——修編譯錯、給建議、取名字。

02
不猜,留洞

資訊不夠就留結構化的洞問人,附上已知的部分。錯的猜測比誠實的空白貴十倍。

03
找一個不會說謊的裁判

我們的裁判是 ng build:機器可驗、不看面子。過關條件是「看起來不錯」的流程,遲早失控。

04
裁判也要驗

編譯通過 ≠ 畫面是對的。單一裁判有盲區,後面再加一層真實瀏覽器實開驗證。

05
閉環,而不是報表

對應一次全系統受惠、答過永不再問、bug 修好變回歸測試——清單只會變短,不會變長。

06
用身分證字號,不用名字

對照關係釘在穩定的 key 上。名字是給人看的,它會改;人做的決定才能沉澱。

Q1 · 原則:能就說能,不能就說不能和為什麼

靜態切版,還是真的互動?

能做得到的
三層互動都是真的

因為產出用的是真的元件庫元件,不是畫出來的樣子。

  • 元件層原生就有:下拉會展開、日期選擇器出面板、必填亮驗證
  • 跳頁自動接線:prototype 連線轉成真路由;選單整份重生,不長重複垃圾
  • 彈窗自動接線:順序無關,目標未產生時留安全待接記號,不會編譯失敗
否做不到的 · 誠實講
業務邏輯不會自動出現

「按下查詢後表格顯示什麼」——Figma 裡根本沒有這個資訊;宣稱能從設計稿生出業務邏輯的工具,都是在猜。

  • 資料接哪裡:manifest 問你;更複雜的行為:「實作」功能白話改碼
  • 沒接 prototype 線的按鈕就是不跳——寧缺勿錯,拍板不做文字比對亂猜
Act 7 · Q&A · 事先收集的問題 2 / 5
SO · 26.08.07 · 19 / 24
Q2 · 下拉選單、彈跳視窗這類元件互動,切得出來嗎

可以,支援得最完整的部分

01
下拉選單

真 select + 選項;選項值從設計稿採收,連收合狀態下藏起來的面板都會去讀;必填自動掛驗證。

02
自動完成

不只產面板,連「打字即時篩選」的邏輯都產好——不然面板永遠列出全部選項。

03
日期選擇器

輸入框 + 日曆按鈕 + 彈出面板,整組接好。

04
彈跳視窗 / 抽屜

彈窗不是一個元件,是一整張 frame 的身分:照 backdrop + dialog 規範畫,自動產成獨立彈窗並接好開窗按鈕。

05
其他有食譜的互動

頁籤、手風琴、步驟條、氣泡提示、下拉按鈕、表格內建分頁……全部食譜合計 29 份。

06
誠實說做不到的

toast 刻意不生成;沒食譜的元件不硬生,留佔位框進待辦;彈窗畫錯,健檢會直接告訴你哪裡不合。

Q3 · 後續頁面維運怎麼進行

HONESTLY
各管一種改動;
長期維運未解。

01
設計稿改了 → 重新產生

不碰程式碼,重填表單即可;答過的答案有記憶

03

AI 改的永遠是專案複本:編譯通過才換回正本,沒通過整份丟掉——正本一個位元組都不會被動到

但書:「實作」改過的頁面重新產生會被覆蓋——系統會蓋「有 AI 改動」的章、用專案鎖擋並發;改動合併本質上沒有漂亮解法

確定性優先,AI 放邊緣

對應一次全系統受惠、答過永不再問、bug 修好變回歸測試——單調收斂,不然只是另一張沒人看的報表。
